## 1. 定位与范围

个人使用的后台自主研发工作台：从 GitHub / GitLab Issue 获取工作，按项目隔离执行，记录每次运行的证据和结果；使用者可以在轻量看板上了解进度、成本与需要自己处理的事项。

### 产品边界

- 保持轻量看板：展示项目、任务、执行轨迹、指标和人工介入入口；不建完整项目管理系统、迭代或组织权限体系。
- 个人是唯一负责人；不做 Agent 市场、IDE 或内置代码编辑器。
- 外部 Runtime 可接入；运行策略可选择 Agent 和模型，不绑定供应商。Runtime 不支持某项能力时明确显示不支持，不静默降级。
- GitHub / GitLab 保留 Issue、PR / MR 等外部事实；本地保存执行证据、配置与统计所需的关联。指标不能反向驱动任务事实。
- 自动 Review、测试、CI 修复、合并必须走可追溯的门禁；人工审批集中到待处理事项，审批必须对应具体交付版本。

### 现有基础与限制

- 单 Symphony 实例按一个 tracker scope 配置；多项目通过独立实例运行，统一观察层聚合。每项目隔离端口、状态目录、工作区、会话和日志，所有写操作依据任务所属实例路由。
- 现有看板仅连接一个 `SYMPHONY_STATE_URL`；Python 实现已有 GitHub / board，Elixir 有 GitLab adapter。不同实现的 GitLab 写入、MR 交付门禁及日志覆盖范围须在该阶段单独验证，不等同于 GitHub 闭环已实现。
- 现有配置 `runtime.model` 为全局值；per-task 路由尚需设计，不能只靠看板标签改变运行中的模型。
- 当前已有 token/运行记录，价格或账单数据不一定有；不可从 token 数推断真实费用。

## 2. 渐进能力与核心契约

| 能力 | 设计方向 | 约束 |
|---|---|---|
| 多项目与扫描 | 各项目独立 tracker 实例，GitHub / GitLab Issue 定时同步；看板按实例聚合 | 每条任务保留 `provider + project + native_id`，不能仅凭 `GH-123` 路由或去重；外部源不可用时标记过期 |
| 拆解与调度 | Agent 可提出子任务建议，经个人确认后写回对应平台；已有调度器负责执行、并发与恢复 | 拆解建议不能自动无限派生；重复扫描不得重复建子任务 |
| Agent / 模型路由 | 运行前依据项目默认策略、显式覆盖、能力/成本约束选择 Runtime 与模型；记录实际选中结果 | 执行中不因配置改变而悄悄切换；不支持的能力显式失败或待人工处理 |
| Review / 测试 / CI | 执行约定的检查；Review 输出含关联 commit / MR / PR 版本；CI 失败按预算返工 | 自动 Review 是额外证据，不代替受保护分支规则或要求的人工 PR Review |
| 风险与合并 | 风险策略将高风险、证据不足和未知结果交个人处理；合并前重新核对授权、SHA、检查与外部状态 | GitLab MR 合并在具备相应门禁前保持人工处理；不沿用旧版本的批准 |
| 全局轨迹与指标 | 各实例输出关联事件，按项目/任务/运行聚合；保留日志与证据链接 | 不将“会话结束”记为成功；未知成本、缺失记录分别展示，避免补零 |

### 执行与数据边界

- 项目唯一键采用 `provider + provider_host + project_id/path`；任务唯一键包含项目键和源任务 ID。运行记录另有不可复用的 run ID，并记录重试序号、Runtime、模型、起止时间、结果与证据位置。
- 个人可以在看板查看和发起对应项目操作；所有修改必须校验任务的项目归属和当前版本，禁止通过当前筛选项决定写入目标。
- 指标口径：成功率按已终结的任务或运行分别统计并标明分母；人工介入数按待处理事件/已处理事件区分；成本分开展示已知金额、token 用量和未知用量，不合并成伪精确总额。可从已有事件/日志推导的先复用现有存储；只有发现跨实例一致性、历史保留或查询成本确实无法满足需求时再评估 SQLite。引入 DB 不意味着必须替换现有收据与恢复机制。
- 每个阶段保持已运行项目可用；新增聚合层故障不能改变原实例的执行或合并决策。归档、配置或路由迁移要先核对存量目录与身份映射；切换前备份，可回退旧单实例看板。

## 3. 建议实施顺序

1. **多项目执行与全局轨迹**：项目隔离、看板聚合、来源身份、只读运行与指标口径；先验证一个 GitHub 项目的兼容性，再接第二项目。
2. **GitHub / GitLab 对齐**：分别验证扫描、任务操作及交付边界；GitLab MR 自动化单独验收。
3. **运行前路由与智能拆解**：可解释的规则路由、模型成本记录；拆解先只生成建议并由个人确认。
4. **自动 Review / 测试与风险门禁**：复用现有 CI 修复与宿主检查逻辑，按交付版本核对，不跳过人工批准策略。

这个顺序不承诺各能力已经落地；逐阶段验收后再扩展下一个边界。

## 4. 验收与验证

| ID | 验收结果 | 验证方式 | 通过标准 |
|---|---|---|---|
| AC01 | 两项目独立运行且看板汇总正确 | 两项目同编号任务、模拟不同源失败与写操作 | 不串任务/目录/日志/写入目标；单源失败显式提示且其他项目可用 |
| AC02 | GitHub、GitLab Issue 可扫描且身份稳定 | 适配器集成与分页/重扫场景 | 重扫无重复，源异常不伪装为空；各平台能力缺口可见 |
| AC03 | 任务拆解与动态路由可追踪 | 草稿确认、配置变更与不支持模型场景 | 未确认不创建任务；每次运行记录实际 Runtime/模型及选择理由 |
| AC04 | 检查、Review 与 CI 修复安全闭环 | 失败、超限、旧 SHA 和重复事件场景 | 审查/修复结果关联交付版本，超限转人工，不发生旧批准复用 |
| AC05 | 风险与合并遵守门禁 | 合并前状态变化、审批撤销和 GitLab 未支持场景 | 不满足门禁不自动合并；结果未知时可观察并等待处理 |
| AC06 | 全局执行轨迹和指标可信 | 跨项目运行、重试、缺失 token/价格、重启场景 | 每次运行可追到证据；成功率分母明确、未知成本不记为零 |

## 5. 确认项

### 阻塞确认项

- 无。个人使用、轻量看板、独立项目实例和渐进实施已由用户表达的产品边界支持；具体跨平台写入与审批行为在各阶段另行设计和确认。

### 非阻塞待确认项

- 第一批真实项目及对应 GitLab 部署环境；不影响首阶段用本地模拟数据验证隔离和聚合。
- 可用 Runtime / 模型及价格来源；首阶段只展示已有 token 和未知成本。
