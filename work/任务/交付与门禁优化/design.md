# 交付与门禁优化

> 设计版本：v1；设计审查：PASS（same-context，1/3）；用户确认：用户回复“确认实施吧”。

## 背景与范围

GH-147 在合并主分支后提交了过期构建产物，导致四个 unit 检查失败；交付后门禁评估借用 runner，占用 Agent 并发槽。看板目前区分 merge_eval，但无法可靠区分实际等待 CI 和等待审批。scenario-test 的 PR CI 对非文档变更运行四组 unit、types 和 browser；文档被整个 workflow 排除。

目标：减少返工和空等、准确展示门禁原因，同时保留基于当前交付 SHA 的检查、高风险人工批准和失败时修复。范围包括 Symphony 调度与看板，以及 scenario-test 的交付检查和 CI；不修改 BUILD_ID 的语义，不以最后一次提交判定整个 PR 风险，不代用户批准。

## 契约与方案

- 交付前由项目现有构建检查确认产物一致；冲突解决或基线更新后重新验证。项目命令由项目配置，不在框架硬编码 npm。
- 宿主独立调度门禁评估，不占 Agent 执行槽；同 issue 同 cycle 只能有一个评估，保留交付 SHA、合并前校验、审批和幂等。失败、超时、重启及 stale cycle 必须可重试，不产生重复合并或错误释放。
- 门禁给看板提供真实判定：检查中、等待批准、需要修复及评估中；状态未知时显示未知，不将所有 merge_poll 推断为待批准。保持旧 API 调用方兼容。
- CI 按整个 PR 相对 base 的变更分层，文档保留轻量校验；不确定或识别失败时执行完整检查。保留稳定汇总检查，区分跳过与未运行、失败，不能因零检查自动放行。对现有无 checks 情况的兼容和迁移须显式验证。
- 低成本审批冒烟使用隔离测试环境，测试本身不得代替人工批准；不新增公开测试 issue 或修改现有活跃 PR。

## 验收

| ID | 结果 | 验证及通过标准 |
|---|---|---|
| AC01 | 合并基线后产物不一致不会交付 | 制造过期产物，项目检查失败；重新构建后一致且通过 |
| AC02 | 门禁等待不占 agent 槽 | 并发上限为 1 时，门禁阻塞期间另一 issue 可执行；同 issue 不重复评估 |
| AC03 | 合并安全 | 校验 SHA 变化、检查失败、无批准、超时、重复与重启；均不错误合并，批准后仅合并一次 |
| AC04 | 页面反映真实原因 | 模拟各门禁态及未知态，API 和页面一致，不将一般等待误标为批准 |
| AC05 | CI 分层保持覆盖 | 文档、源码、混合、构建配置和不确定变更分别验证；汇总门禁对缺失和失败关闭 |

## 风险与审查

同一 checkout 现有大量未提交改动，须保护并在实际 diff 上整合；活跃 GH-147 不重启或干扰。跨仓库修改先在独立工作区准备，不直接推送 master。门禁并发、幂等、恢复及 CI 缺失检查按失败关闭设计；same-context 审查覆盖上述边界，具体现有实现兼容与运行验收留实施阶段核验。
